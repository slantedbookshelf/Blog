一条 SQL 查得慢，不一定是因为语句写得长。有时查询只返回几行，数据库却需要检查大量数据。执行计划能帮助我们看到优化器准备如何访问表、使用哪个索引，以及预计要检查多少行。

下面以 MySQL 8.0 为例。不同数据库的执行计划格式和术语不同，不能直接套用。

## 什么是执行计划

可以把 SQL 看成一份任务清单，而执行计划是数据库选择的完成路线。面对同一个查询，数据库可能选择全表扫描，也可能先走索引；多表查询时，还需要决定表的连接顺序和方式。

优化器会根据统计信息和成本估算选择计划。计划是估算，不保证一定最快，也不等于真实执行过程。

## 用 EXPLAIN 查看计划

在查询前加上 `EXPLAIN`：

```sql
explain
select id, user_id, created_at
from orders
where user_id = 1001
  and created_at >= '2026-01-01';
```

传统格式通常每个访问的表对应一行。也可以用 `EXPLAIN FORMAT=TREE` 查看树形计划。实际输出会随数据量、索引和 MySQL 版本变化，分析时应以自己的结果为准。

## 重点看哪些字段

| 字段 | 含义 | 分析时关注什么 |
| --- | --- | --- |
| `id` | SELECT 的标识 | 辅助区分查询块，不能单凭数字判断完整执行顺序 |
| `select_type` | 查询类型 | 是否包含子查询、派生表等 |
| `table` | 当前访问的表 | 多表查询涉及哪些表 |
| `type` | 表的访问方式 | 是扫描大量数据，还是通过索引缩小范围 |
| `possible_keys` | 可能用于查找的索引 | 候选索引有哪些 |
| `key` | 实际选择的索引 | 是否选择了预期索引；`NULL` 表示没有选择索引 |
| `key_len` | 使用的索引键长度 | 结合字段类型判断索引使用情况，不能只凭长度断定效果 |
| `ref` | 与索引比较的列或常量 | 连接条件或查询条件是否符合预期 |
| `rows` | 预计检查的行数 | 估算扫描范围是否过大 |
| `filtered` | 预计通过表条件过滤的百分比 | `rows × filtered / 100` 可粗略估算传给下一阶段的行数 |
| `Extra` | 额外信息 | 是否有过滤、排序或临时表等操作 |

### 常见的 type

- `const`：通过主键或唯一索引等值条件，最多匹配一行。
- `eq_ref`：连接时对前面每组行，通过主键或非空唯一索引最多匹配一行。
- `ref`：通过非唯一索引等值查找，可能匹配多行。
- `range`：按索引范围查找，例如部分范围条件或 `BETWEEN`。
- `index`：扫描索引，可能仍需扫描大量索引记录。
- `ALL`：全表扫描。

通常越能缩小访问范围越好，但不能只按 `type` 排名判断性能：小表全表扫描可能很合理，最终还要结合数据量和实际耗时。

### 常见的 Extra

`Using index` 通常表示查询所需的列可从索引获取，也就是常说的覆盖索引；`Using where` 表示还需要按条件过滤；`Using filesort` 表示需要额外排序，并不意味着一定写入磁盘；`Using temporary` 表示使用了内部临时表。这些信息是排查线索，不是性能问题的自动判决。

## 从一个查询看优化思路

假设订单表有主键 `id`，经常按用户和时间范围查询：

```sql
select id, user_id, created_at
from orders
where user_id = 1001
  and created_at >= '2026-01-01'
order by created_at;
```

如果执行计划显示 `type = ALL`，且预计检查的行数很大，可以考虑建立联合索引：

```sql
create index idx_orders_user_created
on orders (user_id, created_at);
```

这个索引先按 `user_id` 排列，同一用户内再按 `created_at` 排列，因此可能同时帮助等值过滤、时间范围查找和排序。InnoDB 的二级索引还包含主键列，上面的查询在合适条件下可能成为覆盖索引。

建立索引后重新运行 `EXPLAIN`，比较 `key`、`type`、`rows` 和 `Extra`；再用真实数据测量耗时。优化器不一定选择新索引，例如表很小或条件筛选性较低时，扫描可能更便宜。索引也会增加存储和写入成本，应结合实际查询频率决定是否保留。

## 比较估算和实际执行

MySQL 8.0.18 起可以使用：

```sql
explain analyze
select id, user_id, created_at
from orders
where user_id = 1001
  and created_at >= '2026-01-01';
```

它会真正执行语句，并以树形结果展示各步骤的估算行数、实际行数、耗时和循环次数。多次循环时，显示的时间是每次循环的平均值；分析连接操作时也要关注循环次数，避免只看单次耗时。由于语句会实际执行，应先确认查询的成本和运行环境。

如果估算行数和实际行数差距很大，可以检查统计信息是否过时、数据是否严重倾斜，再结合索引和查询条件分析。执行计划只是起点，优化前后都应该在接近真实的数据量和负载下验证。

## 小结

分析执行计划可以按这个顺序：先确认慢在哪里，再看访问方式、索引和预计扫描行数，接着检查排序与连接，最后用实际执行数据验证修改是否有效。不要为了让某个字段看起来更漂亮而优化，目标始终是让真实业务查询更稳定、更快。
